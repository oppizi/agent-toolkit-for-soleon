# soleon plugin — AHP-1477 release note

This note ships with the AHP-1477 server release (the MCP tools split by
risk), and with the plugin hook that asks before every production-tier tool
(see "Ask before production (plugin hook)").

**Release order.** Publish plugin 1.0.17 only after the AHP-1477 server
release, which registers `call_approved_agent_tool`, is deployed on the env
your `server_url` points at. Before that, every approved call from a pulled
agent fails with "Soleon has no call_approved_agent_tool yet: this plugin
needs the AHP-1477 server release".

## Tools split by risk: what to change

Fifteen Soleon tools used to cover both a safe case and a production case (for
example `promote_agent` with `to_env` set to staging or to prod). Each is now
two tools, one per risk level, and the old name is gone. The name says the
level:

- **Development tier** ends in `_development` (dev only, no environment
  argument) or `_to_staging` (dev to staging, source and target fixed).
- **Production tier** ends in `_production` (staging **and** production; it
  takes `app_env` = `staging` or `prod`) or `_everywhere` (one change that
  every environment uses at once, such as a shared connection or an
  organisation-wide tool policy). `*_production` also matches `*_to_production`.
- `run_eval` becomes `run_eval_checks` (at most 5 agent runs, evals × repeats)
  and `run_eval_suite` (no cap). That is a cost split, not a risk level, so
  neither glob family matches them.
- Two tools are new without retiring anything: `launch_ticket_production`
  (`set_ticket_stage` now refuses the Launch stage and names it), and
  `call_approved_agent_tool` (`call_agent_tool` now refuses a tool marked
  "requires approval"; the approved call is its own tool).

A call to a retired name is refused with a message naming the tools that
replace it and the scope each needs.

### Sign in again

The production-tier tools sit on five new scopes: `soleon-mcp/agent.prod`,
`channel.prod`, `mcp.prod`, `business.prod` and `agent.approve`. A token issued
before this release does not hold them, so the production tools are not listed
for you until you update the plugin and sign in again (`claude mcp login`, or
let the next request open the sign-in). The server still decides what you may
do from your Soleon permissions; the scopes only let it offer the tools.

**If you promote to production today:** update the plugin, sign in again, and
use `promote_agent_to_production` (and `promote_custom_mcp_to_production` for
tool servers, which still go first). The `promote` skill already names them.

### Old rule → new rule

Claude Code rules match tool names, so a rule on a retired name now matches
nothing. Plugin tools are named `mcp__plugin_soleon_soleon__<tool>`. Replace
each old rule with the new names on its row; put the production-tier name
under `ask` or `deny`, never under a broad `allow`.

**A broad allow now reaches production.** An existing
`allow mcp__plugin_soleon_soleon__*` (the rule `/pull-agent` writes into the
project's `.claude/settings.local.json`) matches every new production-tier
tool. Claude Code checks `deny` first, then `ask`, then `allow`, so adding the
`ask` or `deny` rules below on top of it is enough; you do not have to remove
it.

### Paste-ready rules: headless jobs

A `claude -p` job has nobody to answer a prompt, so anything not allowed is
refused, and `deny` is a hard refusal. Paste into the job's
`.claude/settings.json` (or pass the same strings to `--allowedTools` /
`--disallowedTools`). Add any other tool names your job calls to `allow`. The
tiers are listed by exact name, so each rule names one tool.

```json
{
  "permissions": {
    "allow": [
      "mcp__plugin_soleon_soleon__get_*",
      "mcp__plugin_soleon_soleon__list_*",
      "mcp__plugin_soleon_soleon__bind_agent_channel_development",
      "mcp__plugin_soleon_soleon__create_user_automation_development",
      "mcp__plugin_soleon_soleon__delete_user_automation_development",
      "mcp__plugin_soleon_soleon__patch_tool_policy_development",
      "mcp__plugin_soleon_soleon__promote_agent_to_staging",
      "mcp__plugin_soleon_soleon__promote_custom_mcp_to_staging",
      "mcp__plugin_soleon_soleon__publish_custom_mcp_development",
      "mcp__plugin_soleon_soleon__set_agent_active_development",
      "mcp__plugin_soleon_soleon__set_agent_channel_matchers_development",
      "mcp__plugin_soleon_soleon__set_custom_mcp_lifecycle_development",
      "mcp__plugin_soleon_soleon__set_tool_argument_binding_development",
      "mcp__plugin_soleon_soleon__unbind_agent_channel_development",
      "mcp__plugin_soleon_soleon__update_user_automation_development",
      "mcp__plugin_soleon_soleon__update_agent_draft",
      "mcp__plugin_soleon_soleon__patch_agent_draft",
      "mcp__plugin_soleon_soleon__deploy_agent_draft",
      "mcp__plugin_soleon_soleon__run_eval_checks"
    ],
    "deny": [
      "mcp__plugin_soleon_soleon__bind_agent_channel_production",
      "mcp__plugin_soleon_soleon__call_approved_agent_tool",
      "mcp__plugin_soleon_soleon__create_user_automation_production",
      "mcp__plugin_soleon_soleon__delete_user_automation_production",
      "mcp__plugin_soleon_soleon__launch_ticket_production",
      "mcp__plugin_soleon_soleon__patch_tool_policy_everywhere",
      "mcp__plugin_soleon_soleon__promote_agent_to_production",
      "mcp__plugin_soleon_soleon__promote_custom_mcp_to_production",
      "mcp__plugin_soleon_soleon__publish_custom_mcp_production",
      "mcp__plugin_soleon_soleon__set_agent_active_production",
      "mcp__plugin_soleon_soleon__set_agent_channel_matchers_production",
      "mcp__plugin_soleon_soleon__set_custom_mcp_lifecycle_production",
      "mcp__plugin_soleon_soleon__set_tool_argument_binding_everywhere",
      "mcp__plugin_soleon_soleon__unbind_agent_channel_production",

      "mcp__plugin_soleon_soleon__update_user_automation_production"
    ]
  }
}
```

Under these rules the job can edit a dev agent, deploy it to dev, run eval
checks and promote to staging. It cannot promote to production, switch a
staging or production agent on or off, bind a staging channel, change a shared
connection or an organisation-wide tool policy, launch a ticket, or approve a
gated tool call. `run_eval_suite` is left out on purpose (it is the uncapped,
costly run); allow it by name if the job needs it.

`_production` also covers staging: a headless job that must reach staging that
way needs that one name moved from `deny` to `allow` and the hook turned off
in its user settings (below), and it then reaches production too.

### Paste-ready rules: at your desk

The plugin's hook (below) already asks before every production-tier call.
The `ask` block is what keeps that question if you turn the hook off; the
`allow` block saves you a prompt on the development tier. Paste into your user
or project settings.

```json
{
  "permissions": {
    "allow": [
      "mcp__plugin_soleon_soleon__*_development",
      "mcp__plugin_soleon_soleon__*_to_staging",
      "mcp__plugin_soleon_soleon__run_eval_checks"
    ],
    "ask": [
      "mcp__plugin_soleon_soleon__*_production",
      "mcp__plugin_soleon_soleon__*_everywhere",
      "mcp__plugin_soleon_soleon__call_approved_agent_tool"
    ]
  }
}
```

Rules match the tool's name only. Claude Code can also match an argument, but
only as a `--disallowedTools` deny on the command line, never in a settings
file, and only on an exact value, so it is not a substitute for these rules.

The `*` globs sit after the literal server prefix, which Claude Code 2.1.325's
rule validator accepts; the headless rules use exact names instead.

These rules, and the hook below, cover the plugin's server only
(`mcp__plugin_soleon_soleon__…`). If you also added the Soleon MCP server by
hand (for example as `soleon`, giving `mcp__soleon__promote_agent_to_production`),
that server's tools need their own `deny` or `ask` rules on its names
(`mcp__soleon__*_production`, `mcp__soleon__*_everywhere`,
`mcp__soleon__call_approved_agent_tool`); the plugin's hook does not see them.

## Ask before production (plugin hook)

The `soleon` plugin now ships a `PreToolUse` hook, on by default. Before any
Soleon tool whose name ends in `_production` or `_everywhere` (this includes
`*_to_production`), and before `call_approved_agent_tool`, Claude Code asks
you first. The question names the tool, says what it changes, and says how to
turn the hook off. It asks about no other tool: the development tier
(`*_development`, `*_to_staging`), `run_eval_checks`, `run_eval_suite`,
`call_agent_tool` and every read run as before.

The plugin cannot ship permission rules, only hooks, so the hook is a second
line behind your own permission rules, not a replacement for them: keep the
`deny` (headless) or `ask` (desk) rules above. The server still decides what
you may do; the hook only adds the question.

- **At your desk** (default, accept-edits or plan mode) you answer the
  question; nothing else changes.
- **In `claude -p`** nobody can answer, so the call is refused and does not
  run, even when your `allow` rules or `--allowedTools` name the tool. The
  job's output shows the hook's reason (it starts `Soleon:` and names the
  tool), and the call is listed in `permission_denials`.
- **In every other permission mode** (`bypassPermissions`, started with
  `--dangerously-skip-permissions`; `dontAsk`; `auto`, where a classifier
  settles prompts; and any mode Claude Code adds later) the hook answers
  `deny` instead of asking, so the call does not run. It also denies when it
  cannot read the mode at all. It asks only in the modes known to show a
  person the question.
- **If the hook cannot read the tool's name** it still asks (or refuses),
  with a general reason. It never answers "allow".
- **Verified on Claude Code 2.1.325.** A hook that is killed or cannot start
  falls to your permission rules, one more reason to keep them.
- **It covers the plugin's server only**, not a Soleon server you added by
  hand (see the note under the desk rules).
- **It does not cover a pulled agent's own tools.** A pulled agent's tools run
  through a local server the plugin starts (`soleon-agent-tools`), not
  through a `mcp__plugin_soleon_soleon__…` tool, so the hook never sees them.
  When one of those tools is marked "requires approval", the local agent asks
  you in the conversation and then calls it with `approved=true`; that
  approval is asserted by the model, as it is in the Soleon Test Chat. The
  server sends such a call as `call_approved_agent_tool`, so your token needs
  the `agent.approve` scope (sign in again), and every other call, reads
  included, as `call_agent_tool`; only the JSON value `true` counts as an
  approval, and only on a tool marked "requires approval".

### Turning the hook off

Open `/config`, find the soleon plugin's options, and set
`ask_before_production` to `off` (any other value keeps it on). Claude Code
saves it in your user settings (`~/.claude/settings.json`, or
`$CLAUDE_CONFIG_DIR/settings.json`), and the hook honours off only from
there, never from a project's settings (a repository whose settings run
their own hooks can still do anything you can). For a headless job, set it in the
user settings of the account the job runs as.

Off removes the question only where a person would see it (default,
accept-edits or plan mode, and `claude -p` in default mode); in every other
mode the call is still refused. While it is off, each production-tier call
shows a one-line notice. Your own permission rules then decide, so keep the
`deny` (headless) or `ask` (desk) rules above.

## Also in 1.0.17: validation contract regenerated (AHP-1837)

Not part of the tool split; it ships in the same plugin version. The
plugin's offline validator (`plugins/soleon/contract.json`, used by
`deploy-agent`) had stopped matching the platform: its extractor still read the
pre-split admin file, and some of the fields it shipped no longer exist on the
server. It is now regenerated from where each rule lives today
(`lambda/ui_admin_agents/index.py`, `agents_common.py`, the admin shared layer,
`scripts/agent_manager/registry.py`, `shared_keys.py`).

**Removed from the contract — the platform deleted them:**

| Contract key | Why it is gone | What the plugin does now |
|---|---|---|
| `eval_scoring_modes` | Standard evals are graded 0-100, never pass/fail; the platform strips `scoringMode` / `scoreThreshold` | The converter strips `scoringMode`, `scoreThreshold` and `allowSideEffects` from evals; it never emits them |
| `eval_judge_model_allowlist` | Any catalogue model can judge | A `judgeModel` must be a non-empty string; the server checks it against the live catalogue |
| `prompt_cache_ttl_values` | Prompt caching is always on and Soleon picks the duration (AHP-1478) | The converter strips `promptCacheTtl` and `promptCaching`; `deploy-agent` no longer asks about caching |

**Changed values (now matching the server):**

- Visibility: writes accept `public` or `restricted` only. A spec that still
  says `private` is converted to `restricted` (what the server reads `private`
  as); the default is `restricted`, the server's own create default.
- `dynamo_allowed` no longer lists `grantUsers` / `revokeUsers` (the server
  refuses them by name; chat access is the per-environment Restricted list).
- Skills: up to 50 per agent, 256 KB each; `subagentId` and `emptyFolders` are
  accepted skill fields.
- Guardrails: `writeLimitEnabled` joins the enabled switches.
- The skill-id and app-env patterns end in `\Z` (no trailing newline), as on
  the server.
- The platform also accepts the `mock` framework; it is the platform's test
  lane and the plugin does not offer it.

Nothing to do for existing users beyond updating the plugin.
