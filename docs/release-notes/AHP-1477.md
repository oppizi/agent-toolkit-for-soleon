# soleon plugin — AHP-1477 release note

This note ships with the AHP-1477 server release (the MCP tools split by
risk). The ask-before-production hook is documented in its own section, added
with the hook.

## Tools split by risk: what to change

Fifteen Soleon tools used to cover both a safe case and a production case (for
example `promote_agent` with `to_env` set to staging or to prod). Each is now
two tools, one per risk level, and the old name is gone. The name says the
level:

- **Development tier** ends in `_development` (dev only, no environment
  argument) or `_to_staging` (dev to staging, source and target fixed).
- **Production tier** ends in `_production` (staging **and** production; it
  takes `app_env` = `staging` or `prod`) or `_everywhere` (one change that
  every environment uses at once, such as a shared connection or an
  organisation-wide tool policy). `*_production` also matches `*_to_production`.
- `run_eval` becomes `run_eval_checks` (at most 5 agent runs, evals × repeats)
  and `run_eval_suite` (no cap). That is a cost split, not a risk level, so
  neither glob family matches them.
- Two tools are new without retiring anything: `launch_ticket_production`
  (`set_ticket_stage` now refuses the Launch stage and names it), and
  `call_approved_agent_tool` (`call_agent_tool` now refuses a tool marked
  "requires approval"; the approved call is its own tool).

A call to a retired name is refused with a message naming the tools that
replace it and the scope each needs.

### Sign in again

The production-tier tools sit on five new scopes: `soleon-mcp/agent.prod`,
`channel.prod`, `mcp.prod`, `business.prod` and `agent.approve`. A token issued
before this release does not hold them, so the production tools are not listed
for you until you update the plugin and sign in again (`claude mcp login`, or
let the next request open the sign-in). The server still decides what you may
do from your Soleon permissions; the scopes only let it offer the tools.

**If you promote to production today:** update the plugin, sign in again, and
use `promote_agent_to_production` (and `promote_custom_mcp_to_production` for
tool servers, which still go first). The `promote` skill already names them.

### Old rule → new rule

Claude Code rules match tool names, so a rule on a retired name now matches
nothing. Plugin tools are named `mcp__plugin_soleon_soleon__<tool>`. Replace
each old rule with the new names on its row; put the production-tier name
under `ask` or `deny`, never under a broad `allow`.

**A broad allow now reaches production.** An existing
`allow mcp__plugin_soleon_soleon__*` (the rule `/pull-agent` writes into the
project's `.claude/settings.local.json`) matches every new production-tier
tool. Claude Code checks `deny` first, then `ask`, then `allow`, so adding the
`ask` or `deny` rules below on top of it is enough; you do not have to remove
it.

### Paste-ready rules: headless jobs

A `claude -p` job has nobody to answer a prompt, so anything not allowed is
refused, and `deny` is a hard refusal. Paste into the job's
`.claude/settings.json` (or pass the same strings to `--allowedTools` /
`--disallowedTools`). Add any other tool names your job calls to `allow`.

```json
{
  "permissions": {
    "allow": [
      "mcp__plugin_soleon_soleon__get_*",
      "mcp__plugin_soleon_soleon__list_*",
      "mcp__plugin_soleon_soleon__*_development",
      "mcp__plugin_soleon_soleon__*_to_staging",
      "mcp__plugin_soleon_soleon__update_agent_draft",
      "mcp__plugin_soleon_soleon__patch_agent_draft",
      "mcp__plugin_soleon_soleon__deploy_agent_draft",
      "mcp__plugin_soleon_soleon__run_eval_checks"
    ],
    "deny": [
      "mcp__plugin_soleon_soleon__*_production",
      "mcp__plugin_soleon_soleon__*_everywhere",
      "mcp__plugin_soleon_soleon__call_approved_agent_tool"
    ]
  }
}
```

Under these rules the job can edit a dev agent, deploy it to dev, run eval
checks and promote to staging. It cannot promote to production, switch a
staging or production agent on or off, bind a staging channel, change a shared
connection or an organisation-wide tool policy, launch a ticket, or approve a
gated tool call. `_production` covers staging too: a job that must switch on
or bind in staging allows those exact names, for example
`mcp__plugin_soleon_soleon__set_agent_active_production`, and accepts that the
same tool also reaches production. `run_eval_suite` is left out on purpose
(it is the uncapped, costly run); allow it by name if the job needs it.

### Paste-ready rules: at your desk

The same split, with Claude Code asking you before every production-tier call.
Paste into your user or project settings.

```json
{
  "permissions": {
    "allow": [
      "mcp__plugin_soleon_soleon__*_development",
      "mcp__plugin_soleon_soleon__*_to_staging",
      "mcp__plugin_soleon_soleon__run_eval_checks"
    ],
    "ask": [
      "mcp__plugin_soleon_soleon__*_production",
      "mcp__plugin_soleon_soleon__*_everywhere",
      "mcp__plugin_soleon_soleon__call_approved_agent_tool"
    ]
  }
}
```

Rules match the tool's name only. Claude Code can also match an argument, but
only as a `--disallowedTools` deny on the command line, never in a settings
file, and only on an exact value, so it is not a substitute for these rules.

## Validation contract regenerated from current platform source (AHP-1837)

The plugin's offline validator (`plugins/soleon/contract.json`, used by
`deploy-agent`) had stopped matching the platform: its extractor still read the
pre-split admin file, and some of the fields it shipped no longer exist on the
server. It is now regenerated from where each rule lives today
(`lambda/ui_admin_agents/index.py`, `agents_common.py`, the admin shared layer,
`scripts/agent_manager/registry.py`, `shared_keys.py`).

**Removed from the contract — the platform deleted them:**

| Contract key | Why it is gone | What the plugin does now |
|---|---|---|
| `eval_scoring_modes` | Standard evals are graded 0-100, never pass/fail; the platform strips `scoringMode` / `scoreThreshold` | The converter strips `scoringMode`, `scoreThreshold` and `allowSideEffects` from evals; it never emits them |
| `eval_judge_model_allowlist` | Any catalogue model can judge | A `judgeModel` must be a non-empty string; the server checks it against the live catalogue |
| `prompt_cache_ttl_values` | Prompt caching is always on and Soleon picks the duration (AHP-1478) | The converter strips `promptCacheTtl` and `promptCaching`; `deploy-agent` no longer asks about caching |

**Changed values (now matching the server):**

- Visibility: writes accept `public` or `restricted` only. A spec that still
  says `private` is converted to `restricted` (what the server reads `private`
  as); the default is `restricted`, the server's own create default.
- `dynamo_allowed` no longer lists `grantUsers` / `revokeUsers` (the server
  refuses them by name; chat access is the per-environment Restricted list).
- Skills: up to 50 per agent, 256 KB each; `subagentId` and `emptyFolders` are
  accepted skill fields.
- Guardrails: `writeLimitEnabled` joins the enabled switches.
- The skill-id and app-env patterns end in `\Z` (no trailing newline), as on
  the server.
- The platform also accepts the `mock` framework; it is the platform's test
  lane and the plugin does not offer it.

Nothing to do for existing users beyond updating the plugin.
